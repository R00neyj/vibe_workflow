# wf-init — 정의 단계

바이브코딩이 뒤늦은 대규모 리팩터링으로 끝나는 원인은 **입력물이 없는 상태에서 구현이 먼저 시작되기 때문**이다. 이 스킬은 파이프라인의 입력물(요구사항·아키텍처·백로그)을 사람과 함께 만들어 고정한다.

`WFCTL` = `node "${CLAUDE_PLUGIN_ROOT}/scripts/wfctl.js"`

## 절대 규칙

- 이 단계에서 **소스 코드를 쓰지 않는다.** 훅이 차단하지만, 차단 전에 시도조차 하지 마라.
- 모르는 것을 추측해서 문서에 적지 않는다. 반드시 `AskUserQuestion` 으로 묻는다.
- 기존 코드가 있는 프로젝트라면, 코드를 읽고 확인한 사실만 적는다.

## 절차

### 1. 설치

```
WFCTL init
```

이미 `.workflow` 가 있으면 멈추고 사용자에게 `--force` 여부를 묻는다.
설치 후 감지된 자동 체크 목록을 사용자에게 보고한다. 감지된 것이 없으면 5단계에서 직접 채운다.

### 2. 현황 파악 (기존 프로젝트인 경우만)

빈 디렉터리가 아니면 먼저 읽는다: README, 패키지 매니페스트, 진입점, 디렉터리 구조.
읽지 않고 아키텍처 문서를 쓰지 마라.

### 3. 요구사항 문답

`.workflow/requirements.md` 의 각 절을 채우기 위해 **AskUserQuestion 으로 묻는다.** 한 번에 최대 4문항씩, 필요한 만큼 라운드를 반복한다.

반드시 답을 받아야 하는 것:

1. **문제** — 무엇이 불편한가. 지금은 그 일을 어떻게 처리하는가.
2. **사용자** — 누가 쓰는가. 혼자 쓰는가, 배포하는가.
3. **범위 제외** — *만들지 않을 것*. 이 항목이 비면 범위는 반드시 새어나간다.
4. **성공 기준** — 무엇이 참이면 끝난 것인가.
5. **제약** — 실행 환경, 런타임, 성능, 데이터 보관, 배포 방식.

답이 "적당히 알아서"로 돌아오면 선택지를 만들어 다시 묻는다. 그래도 정해지지 않으면 **가정으로 명시해 문서에 남긴다** — 빈칸으로 두지 않는다.

작성 후 사용자에게 요약 보고하고 확인을 받는다.

### 4. 아키텍처 확정

`.workflow/architecture.md` 를 채운다. 핵심은 세 가지다.

- **구성 요소와 책임** — 이름과 위치까지
- **의존 방향** — 여기 없는 방향의 import 는 위반으로 취급된다
- **불변조건** — 깨지면 버그가 아니라 설계 위반인 것들

기술 선택은 대안과 함께 근거를 적는다. 선택이 갈리는 지점은 `AskUserQuestion` 으로 사용자가 고르게 한다.

### 5. 검증 수단 확정

`.workflow/config.json` 의 `checks` 를 확정한다. 자동 체크가 하나도 없으면 verify 단계가 사실상 사람 확인만 남는다. 최소 하나는 만든다.

- 테스트 프레임워크가 없으면 도입 여부를 묻는다
- 타입체커·린터가 있으면 명령을 채운다
- `sourceGlobs` 를 실제 소스 경로로 좁힌다 (기본값 `**` 는 너무 넓다)

### 6. 백로그 분해

`.workflow/backlog.yaml` 을 채운다.

- 한 항목은 **독립적으로 검증 가능한 크기**여야 한다. 여러 날 걸릴 것 같으면 쪼갠다.
- 각 항목에 `done_when` 을 관찰 가능한 서술로 적는다
- `blocked_by` 로 순서를 표현한다

분해가 끝나면 사용자에게 착수 순서를 제안하고 동의를 받는다.

### 7. 첫 task 착수

```
WFCTL task-new "<첫 백로그 항목 제목>"
```

단계가 자동으로 `plan` 으로 전이된다. 이어서 `/wf-plan` 을 안내한다.

## 완료 보고

다음을 사용자에게 알린다: 생성된 문서 경로, 확정된 자동 체크, 백로그 항목 수, 다음 명령(`/wf-plan`).
