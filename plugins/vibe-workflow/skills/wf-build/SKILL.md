# wf-build — 구현

승인된 계획을 그대로 옮기는 단계다. **여기서 새로 판단하지 않는다.**

`WFCTL` = `node "${CLAUDE_PLUGIN_ROOT}/scripts/wfctl.js"`

## 절대 규칙

- **계획에 없는 것을 만들지 않는다.** 개선하고 싶은 것이 보이면 `backlog.yaml` 에 추가만 하고 지나간다.
- 계획과 실제가 어긋나면 **코드를 바꾸지 말고 멈춘다.** 사용자에게 알리고 계획 수정을 제안한다.
- 검증 없이 턴을 끝내지 않는다. Stop 훅이 막는다.

## 절차

### 1. 전제 확인

```
WFCTL status
```

`계획 승인` 이 `approved` 가 아니면 코드 쓰기가 차단된다. `/wf-review` 로 돌아간다.
단계가 `build` 가 아니면 `WFCTL phase build --task <id>` 로 전이한다.

### 2. 계획 재확인

`.workflow/tasks/<task>/plan.md` 를 다시 읽는다. 특히:

- 변경 파일 목록
- 공개 인터페이스 시그니처 — **적힌 그대로** 구현한다
- 수용 기준 — 구현 중 이것을 계속 참조한다
- "하지 않는 것" — 이 목록을 어기지 않는다

### 3. 구현

작은 단위로 나눠 진행한다. 파일 하나를 크게 뜯어고치는 것보다, 검증 가능한 조각으로 나누는 편이 되돌리기 쉽다.

지키는 것:

- 주변 코드의 스타일·명명·주석 밀도를 따른다
- 계획에 있는 예외/실패 경로를 빠뜨리지 않는다
- 아키텍처의 의존 방향을 어기지 않는다

**계획 이탈이 필요해지면** — 그 자리에서 판단하지 말고 멈춘다. 무엇이 어긋났는지, 어떤 수정이 필요한지 사용자에게 보고한다. 사용자가 동의하면 `WFCTL phase plan` 으로 되돌아가 계획을 고치고 재승인을 받는다.

### 4. 자체 확인

구현이 끝나면 계획의 수용 기준을 하나씩 짚어 대조한다. 빠진 것이 있으면 지금 채운다.

### 5. 검증으로 넘기기

```
WFCTL phase verify
```

이어서 `/wf-verify` 를 실행한다. 코드를 고쳐놓고 여기서 턴을 끝내면 Stop 훅이 차단한다.

## 차단당했을 때

훅이 쓰기를 막았다면 이유는 셋 중 하나다.

| 사유 | 조치 |
| --- | --- |
| 단계가 build 가 아님 | `WFCTL phase build --task <id>` |
| 계획 미승인 | `/wf-review` 로 승인 받기 |
| 계획에 없는 파일 | plan.md 의 `files` 를 고치고 재승인, 또는 그 파일을 건드리지 않기 |

**차단을 우회로 뚫는 것을 먼저 시도하지 마라.** 차단은 대개 계획이 부족하다는 신호다.
