# wf-verify — 기능 검증

`WFCTL` = `node "${CLAUDE_PLUGIN_ROOT}/scripts/wfctl.js"`

## 절대 규칙

- **실행하지 않은 항목에 `pass` 를 적지 않는다.** 이 규칙 하나가 무너지면 파이프라인 전체가 무의미해진다.
- 실패는 실패로 적는다. 고친 뒤 다시 검증한다.
- 사람 확인 항목을 대신 통과시키지 않는다.

## 절차

### 1. 자동 체크 실행

```
WFCTL check
```

`config.json` 에서 켜진 체크를 실제로 실행하고 종료 코드로 판정한다.
결과는 `.workflow/tasks/<task>/checks.json` 에도 남는다.

실패한 체크가 있으면:

1. 출력을 읽고 원인을 파악한다
2. `WFCTL phase build` 로 되돌아가 고친다
3. 다시 `WFCTL check`

**실패를 verify.md 에 fail 로 적고 넘어가는 것은 최후 수단이다.** 그 경우 남기는 이유를 "남은 문제" 절에 반드시 적는다.

### 2. 수용 기준 대조

`plan.md` 의 수용 기준을 그대로 옮겨 하나씩 확인한다. 각 항목에 대해:

- 무엇을 실행/관찰해서 확인했는가
- 결과가 무엇이었는가

자동 체크가 통과했다는 사실이 수용 기준 충족을 뜻하지는 않는다. 별도로 확인한다.

### 3. 에이전트 검증

변경된 코드를 계획과 대조해 직접 검토한다. 세 가지를 찾는다:

- **계획에 없는데 들어간 변경** — 범위 이탈
- **계획에 있는데 빠진 변경** — 누락
- **결함** — 예외 경로 미처리, 경계값, 기존 호출부 파손

변경 목록은 `git diff` 로 확인한다. git 저장소가 아니면 `.workflow/dirty.txt` 를 참고한다.

### 4. 사람 확인 요청

자동화로 판정할 수 없는 항목(화면, 사용 흐름, 문구, 실제 데이터 동작)을 정리해 사용자에게 보여주고 `AskUserQuestion` 으로 확인을 받는다.

무엇을 어떻게 확인해야 하는지 **구체적으로** 알려준다. "확인해주세요"만으로는 부족하다.

### 5. 리포트 작성

`.workflow/tasks/<task>/verify.md` 를 템플릿 형식으로 쓴다.
`wf:verify` 마커에 각 항목의 `pass`/`fail` 을 적는다 — **`WFCTL check` 출력을 근거로**.
이 쓰기는 권한 프롬프트로 올라간다.

`config.json` 에서 켜진 항목만 요구된다. 요구 항목은 `WFCTL status` 에서 확인할 수 있다.

### 6. 마무리

전부 `pass` 면:

```
WFCTL clear-dirty
```

그리고 `backlog.yaml` 의 해당 항목을 `status: done` 으로 갱신한다.
다음 항목이 있으면 `WFCTL task-new "<다음 제목>"` 으로 루프를 다시 돈다.

## Stop 훅에 막혔을 때

"소스를 수정했지만 검증이 끝나지 않았다" 는 차단은 정상 동작이다.
미충족 항목을 확인하고(`WFCTL status`) 채운다. 3회 연속 막히면 훅이 통과시키되 경고를 남긴다 — 그 경고를 무시하지 마라.
