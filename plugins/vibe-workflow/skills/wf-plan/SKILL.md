# wf-plan — 계획 수립

`WFCTL` = `node "${CLAUDE_PLUGIN_ROOT}/scripts/wfctl.js"`

## 절대 규칙

- 이 단계에서 **소스 코드를 쓰지 않는다.** 훅이 차단한다.
- **경로를 지어내지 마라.** plan.md 에 적는 모든 파일 경로는 실제로 확인한 것이거나, 새로 만들 것임을 명시한 것이어야 한다.
- 수용 기준은 관찰 가능해야 한다. "잘 동작한다", "안정적이다" 같은 표현은 금지.

## 절차

### 1. 상태 확인

```
WFCTL status
```

`.workflow` 가 없으면 `/wf-init` 을 먼저 하라고 안내하고 멈춘다.

### 2. task 확보

현재 task 가 없거나 새 작업이면:

```
WFCTL task-new "<작업 제목>"
```

무엇을 할지 정해지지 않았으면 `.workflow/backlog.yaml` 에서 `blocked_by` 가 빈 항목들을 보여주고 사용자가 고르게 한다.

### 3. 현재 코드 읽기

계획을 쓰기 **전에** 관련 코드를 읽는다. 최소한:

- 수정 대상이 될 파일들의 현재 동작
- 호출부(누가 이 코드를 쓰는가)
- `.workflow/architecture.md` 의 불변조건과 의존 방향

읽은 내용을 plan.md 의 "현재 상태" 표에 사실로 기록한다.

### 4. plan.md 작성

`.workflow/tasks/<task>/plan.md` 를 채운다. 빈 절을 남기지 마라.

특히 중요한 세 가지:

**`wf:plan` 마커의 `files`** — 이 task 에서 건드릴 경로를 쉼표로 구분해 적는다.
`config.json` 의 `restrictToPlannedFiles` 가 true 면 여기 없는 파일 쓰기가 차단된다.

**수용 기준** — 각 항목이 "무엇을 어떻게 확인하면 참인지" 판정 가능해야 한다. 검증 방법 표와 1:1 로 대응시킨다.

**하지 않는 것** — 손대고 싶지만 참을 것을 명시한다. 이 절이 비어 있으면 build 단계에서 범위가 샌다. 참는 항목 중 해야 할 것은 `backlog.yaml` 에 추가한다.

### 5. 자기 점검

제출 전에 스스로 확인한다. 하나라도 아니면 고친다.

- [ ] 모든 파일 경로가 실재하거나 신규임이 명시되었는가
- [ ] 수용 기준마다 대응하는 검증 수단이 있는가
- [ ] 아키텍처의 의존 방향을 어기지 않는가
- [ ] 실패·예외 경로가 계획에 있는가
- [ ] 롤백 방법이 적혀 있는가
- [ ] 더 작게 쪼갤 수 있는데 안 쪼갠 것은 아닌가

### 6. 검토로 넘기기

```
WFCTL phase review
```

사용자에게 `/wf-review` 를 안내한다. **스스로 승인하지 마라** — 승인은 review 단계에서 사람이 한다.
